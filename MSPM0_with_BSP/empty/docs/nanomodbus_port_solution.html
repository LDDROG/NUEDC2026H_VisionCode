2. 逐条分析与决策

Issue #1：单一全局实例（g_port_ctx / g_server / g_bound_usart）

✅ 判定：接受现状，不做修改

分析

  • 当前 g_port_ctx、g_server、g_bound_usart 是全局静态变量，确实只支持一个 Modbus 实例。
  • 但 MSPM0G3507 上只有一个 UART 用于 Modbus（UART_0_INST），不存在多总线需求。
  • nanoMODBUS 核心库已经通过 conf.arg 机制传递用户数据——当前 port 层已正确使用此机制（conf.arg = &g_port_ctx）。
  • 如果未来需要多实例，只需将全局变量改为堆分配的 NMBSPortContext*，改动量约 30 行，不需要架构变更。

结论

当前单实例设计完全满足需求。多实例扩展是线性改动，不需要提前重构。

Issue #2：客户端发送前清空接收队列

✅ 判定：接受现状，行为正确

分析

关键代码（port.c:455-458）：

if (ctx->is_client)
{
    NMBSRingQueueReset(&ctx->rx_queue);  // ← 被质疑的代码
}

这是 Modbus RTU 半双工协议的正确行为：

  1. 客户端发送请求前，总线上可能残留之前的响应帧（如超时未读完的帧、噪声数据等）。
  2. 如果不清理，read_serial() 会读到旧数据，导致 CRC 校验失败或解析错误。
  3. 清理时机在 USARTSend() 之前是正确的——此时总线空闲，不会有新数据到达。
  4. 即使有竞争（理论上不太可能），下一轮请求-响应周期会自动纠正。

实际上这是一个防御性设计，不是 bug。

Issue #3：阻塞式发送

✅ 判定：接受现状，后续可选优化

分析

波特率典型 RTU 帧长发送耗时
96008 字节~8.3 ms
1152008 字节~0.7 ms
115200256 字节~22 ms
  • Modbus RTU 典型帧长 8-256 字节，115200 波特率下阻塞 <1ms（小帧）到 22ms（最大帧）。
  • 当前 main 循环是单任务架构（无 FreeRTOS 调度），阻塞无实际影响。
  • 改为 DMA 发送需要增加发送完成回调、状态机、错误处理，代码量增加约 50 行，收益不大。

结论

当前阻塞发送在单任务架构下完全可用。仅在引入 FreeRTOS 多任务且 Modbus 需与其他高优先级任务共存时才需要优化。

Issue #4：回调链只保存一层

✅ 判定：接受现状，场景不适用

分析

NMBSPortAttachCallback() 保存旧回调为 chained_callback，如果 USART 实例已被其他模块挂载，旧回调会被覆盖。

但在 Modbus RTU 场景下：

  • Modbus 使用的 UART 是点对点独占的（RS485 总线），不会与其他协议共享同一 UART。
  • nmbs_port_set_usart_instance() 用于绑定外部已注册的 USART 实例，此时旧回调确实需要链式调用——当前实现已正确处理。
  • 如果确实需要多层回调，应由 BSP 层（bsp_usart）提供回调链表机制，而非 port 层实现。

Issue #5：超时精度

🔧 判定：小幅修改（补充注释 + 可选精度检查）

分析

当前 NMBSPortWaitUsartReady() 和 read_serial() 使用 TimeGetBootMs() 做毫秒级超时。这是正确的——byte_timeout_ms 参数本身就是毫秒单位。

唯一隐患：TimeGetBootMs() 内部是 TimeGetTick() / 1000，如果 SysConfig 中 TIMG12 预分频配置错误（非 1μs/tick），超时时间会偏离。但这不是 port 层的问题，而是 Time 模块的问题。

修改内容

在 NMBSPortWaitUsartReady() 和 read_serial() 中添加注释说明时间精度依赖 TimeGetBootMs() 的配置正确性。

Issue #6：PushBytes / PopBytes 逐字节循环

✅ 判定：接受现状，无需优化

分析

NMBSRingQueuePushBytes() 内部是逐字节调用 NMBSRingQueuePush() 的循环。理论上可以用 memcpy + 批量指针移动优化。

但实际影响：

  • Modbus RTU 最大帧长 256 字节，115200 波特率下每秒最多约 450 帧。
  • 每帧 PushBytes 最多循环 256 次，每次约 10 个 CPU 周期（MSPM0 @80MHz），单帧耗时约 32μs。
  • 占 CPU 时间 0.16%，完全不是瓶颈。
  • 环形队列的 wrap-around 特性使 memcpy 优化复杂化（需要分两段拷贝），代码可读性下降。

Issue #7：head/tail 无符号溢出

✅ 判定：无问题，设计正确

head 和 tail 是 uint16_t，持续递增会溢出回 0。但 head - tail（无符号减法）在溢出场景下仍然正确：

// 假设 head=0x0002, tail=0xFFFE（tail 刚溢出回绕）
// available = head - tail = 0x0002 - 0xFFFE = 0x0004（正确）

这是环形队列的经典实现方式，无需修改。

Issue #8：server_write_single_coil 参数语义

✅ 判定：无问题，实现正确

关键代码：

uint8_t coil = value ? 0x01U : 0x00U;
return server_write_multiple_coils(address, 1U, &coil, unit_id, arg);

nmbs_bitfield_write() 宏只看 bit 0（(v) << ((b) & 7)），所以 0x01 和 0xFF 效果相同。这是正确的。

Issue #9：无 RTU 地址校验

🔧 判定：小重构，添加校验

分析

Modbus RTU 规范规定：

  • 有效从机地址：1-247
  • 地址 0：广播地址（所有从机接收但不响应）
  • 地址 248-255：保留

当前 nmbs_server_init() 直接使用 server->id，无范围检查。如果用户传入 0 或 255，会导致不可预期行为。

修改内容

在 nmbs_server_init() 开头添加 3 行校验代码。

Issue #10：日志格式 %u vs PRIu32

🔧 判定：小幅修改，提升可移植性

当前 LOGWARNING("... dropped=%u", (unsigned int)g_port_ctx.dropped_bytes) 已经将 uint32_t 强转为 unsigned int，在 32 位平台上完全正确。

改为 PRIu32 更规范，但无功能影响。

3. 实施方案（代码级）

3.1 RTU 地址校验（Issue #9）

修改文件：port.c

修改位置：nmbs_server_init() 函数开头

修改前

nmbs_error nmbs_server_init(nmbs_t *nmbs, nmbs_server_t *server)
{
    nmbs_platform_conf conf;
    nmbs_callbacks cb;
    nmbs_error status;

    if ((nmbs == NULL) || (server == NULL))
    {
        return NMBS_ERROR_INVALID_ARGUMENT;
    }

修改后

nmbs_error nmbs_server_init(nmbs_t *nmbs, nmbs_server_t *server)
{
    nmbs_platform_conf conf;
    nmbs_callbacks cb;
    nmbs_error status;

    if ((nmbs == NULL) || (server == NULL))
    {
        return NMBS_ERROR_INVALID_ARGUMENT;
    }

    /* Modbus RTU 有效从机地址: 1-247 (0=广播, 248-255=保留) */
    if ((server->id == 0U) || (server->id > 247U))
    {
        return NMBS_ERROR_INVALID_ARGUMENT;
    }

改动量：+4 行

4. 结论

核心判断：不需要重构，3 处小幅修改即可

类别数量说明
直接修改2 处RTU 地址校验（+4 行）、日志格式（+2 行）
小重构0 处原判定的超时精度问题实际无需代码改动，补充注释即可
接受现状5 处全局实例、清空队列、阻塞发送、回调链、逐字节循环
无问题2 处head/tail 溢出、coil 参数语义

为什么不需要重构

  1. 全局实例：当前单 UART 单总线场景完全够用。多实例扩展是线性改动（改全局变量为堆分配指针），不涉及架构变更。
  2. 清空队列：这是 Modbus RTU 半双工协议的正确行为，不是 bug。
  3. 阻塞发送：单任务架构下无影响，RTU 帧短（<1ms@115200）。
  4. 回调链：Modbus UART 独占使用，不会多层挂载。
  5. 性能问题：115200 波特率下逐字节循环完全不是瓶颈。

实际需要改的代码

// port.c nmbs_server_init() 开头加 4 行:
if ((server->id == 0U) || (server->id > 247U))
{
    return NMBS_ERROR_INVALID_ARGUMENT;
}

总共 6 行代码改动（含注释和 include），0 处架构变更。
